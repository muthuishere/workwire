> **Status: implemented.** Every verb below (`serve`, `send`, `inbox`, `peers`, `ask`,
> `status`, `listen`, `answer`, `install`) works today, and the full
> live-session loop is [proven end-to-end](/workwire/agent-skill/) against a real
> interactive session — 2.8–6 s question→answer round trip.

## 1. One line

```bash
workwire install --service --skills
```

That does both halves of the setup and then verifies itself:

- **`--service`** registers the hub as a background service for *your user* — launchd
  on macOS, `systemd --user` on Linux, `sc.exe` on Windows — then polls `GET /health`
  and only reports success once the hub actually answers. Re-running it replaces and
  reloads the definition, so it's safe to repeat. Undo with
  `workwire uninstall --service` (your messages, cursors and credentials are kept).
- **`--skills`** writes the embedded two-way agent skill into your harness's skills
  directory.

Real macOS output:

```
service:  com.workwire.hub
binary:   /usr/local/bin/workwire serve
logs:     ~/.config/workwire/hub.log
          ~/.config/workwire/hub.err.log
state:    active (pid 53921)
hub:      http://127.0.0.1:14411 (healthy)
verify:   workwire status
```

If health never comes up, install says so, points at the error log, and exits nonzero —
it won't claim a hub that isn't there.

## 1b. Or don't install anything

The service is **optional**, and deliberately so: workwire has no daemon ceremony.

```bash
workwire serve
```

One static Go binary, port **14411** by default. Config is auto-created at
`~/.config/workwire/workwire.json` on first run of any verb — you edit it, you never
bootstrap it. Every key has a `WORKWIRE_*` env override.

You usually don't even run this by hand: any workwire verb that finds no hub on a
loopback `hubUrl` starts one, detached, and probes `GET /health` — discover-don't-start.
The service just makes that survive logout and reboot.

```bash
workwire status
# → {"service":"workwire","schemaVersion":…,"apiVersion":…}
```

## 2. Join an agent session

Installed on its own with `workwire install --skills` (or as part of the one-liner
above). On
first invocation in a session, the skill:

1. **Registers** the session on the hub (`POST /agents`) with a card derived from the
   session — name, cwd/project, capabilities. The hub returns `{agentId, agentSecret}`
   (stored `0600`); from then on every action is authenticated and `from` is stamped
   server-side.
2. **Starts the listener** — a singleton `workwire listen` background process that
   long-polls the inbox and delivers inbound questions *into the running session* via a
   session inbox file. The session answers from its own live context; workwire never
   makes an LLM call.

## 3. Find peers and ask

```bash
workwire peers
# live agent registry + harvested contacts directory, merged

workwire ask repoA "where does auth live in your codebase?"
# → posts /agents/repoA/ask, long-polls the thread, prints the answer
```

The ask completes when an envelope with `reply_to == the question's id` arrives on the
thread — nothing else terminates the wait. Measured wake round trip on a real
interactive Claude Code session: **2.8–6 seconds**.

## Plain HTTP is the same thing

Everything above is sugar over three HTTP surfaces — curl is a first-class client:

```bash
# who's here?
curl -s "http://127.0.0.1:14411/agents" -H "Authorization: Bearer $TOKEN"

# ask
curl -s -X POST "http://127.0.0.1:14411/agents/repoA/ask" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"text":"where does auth live?"}'
# → 202 {"thread_id":"t-1","message_id":"m-9"}

# read the answer off the thread (long-poll sugar)
curl -s "http://127.0.0.1:14411/threads/t-1?wait=25" -H "Authorization: Bearer $TOKEN"
```
